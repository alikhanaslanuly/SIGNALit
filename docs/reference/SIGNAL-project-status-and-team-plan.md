# SIGNAL — состояние проекта и задачи команды

**Срез:** 28 сентября 2026 года, `main` после PR #8 (`1178059`). Документ описывает состояние кода и известные проверки на эту дату. Роли A/B/C/D взяты из командного плана; конкретные исполнители могут поменяться.

## Коротко

SIGNAL — браузерный прототип для общения пациента, которому трудно говорить, с медсестрой через шесть жестов одной руки. Основной локальный сценарий работает: камера → 21 ориентир MediaPipe → собственные признаки и классификатор → удержание жеста → тренировка или диалог → семантическое сообщение → dashboard → статус обратно пациенту. Это **демо-прототип**, а не проверенный медицинский инструмент или замена кнопки вызова персонала.

**Статус:** локальная сборка и автоматические тесты проходят; публичный деплой поставлен на паузу по решению команды. Перед показом жюри нужны повторная проверка с реальной камерой, прогон двух вкладок и проверка конечного HTTPS-адреса после разрешения на публикацию.

**Маршруты:** `/` — пациент и медсестра на одной странице; `/patient` и `/dashboard` — две вкладки на одном origin. `?debug=1` включает mock-контролы только в dev-сборке. Диагностика камеры доступна в dev по `/src/core/vision/dev/`.

### Что проверено вручную

- В локальном Chrome/Edge один участник видел изображение камеры и ориентиры руки, прошёл тренировку и отправил намеренный PAIN; статусы запроса дошли до завершения.
- Интерфейс проверен на ширинах 390, 768, 1024 px и desktop; горизонтального переполнения в проверенных состояниях не было. Mock-сценарий `PENDING → ACKNOWLEDGED → COMPLETED` и экран результата пройдены.

Эти проверки подтверждают работоспособность конкретного демо-окружения. Они **не измеряют** точность распознавания для разных людей и устройств. В fixtures сейчас 11 стабильных записей **одного** участника (есть все шесть жестов и обе руки); тест 11/11 на них — регрессия, не метрика качества модели.

## Передача задач сокомандникам

Каждую задачу выполнять в отдельной ветке с коротким PR. При изменении `src/contracts/` сначала согласовать интерфейс со всеми затронутыми ролями. Указывать в PR: что изменилось, как проверено, известные ограничения.

| Роль | Следующая задача | Критерий готовности |
| --- | --- | --- |
| **A — Vision Lead** | **P0:** прогон на демо-камере: YES, NO, HELP, PAIN, TOILET, WATER; обе руки, несколько расстояний и световых условий. Зафиксировать FPS и ошибки в таблице. **P1:** собрать согласованные и обезличенные fixtures от других участников; настроить пороги только после разделения участников на tuning/evaluation. | По каждому жесту есть число попыток, успешных подтверждений, ложных подтверждений и время удержания; новые fixtures проходят тесты, регрессий на старых нет. |
| **B — Logic & Error Mode Lead** | **P0:** проверить на реальной камере приоритет подсказок и отсутствие мерцания, особенно при переходе между позами. **P1:** совместно с A решить, какие результаты калибровки действительно применить к распознаванию; не менять пороги на глаз. | Подсказка описывает исправимое действие, не перекрывает успешный жест; тесты фиксируют выбранные пороги и переходы. |
| **C — Experience Lead** | **P0:** провести короткий сценарий с 1–2 людьми, не участвовавшими в разработке: найти кнопку камеры, понять подсказку, отправить запрос, увидеть ответ медсестры. **P1:** подготовить RU/EN-тексты для dashboard и мобильных переключателей, проверить клавиатуру и крупный шрифт. | Человек проходит сценарий без подсказок разработчика; критичные непонятные места записаны и исправлены; тексты переданы D для интеграции в dashboard. |
| **D — Product & Platform Lead** | **P0:** прогнать сценарий одной страницы и двух вкладок, подготовить демонстрационный скрипт и запасные скриншоты; проверить конфликт статусов и повторное открытие вкладки. **P1:** подключить тексты C в dashboard. **Перед публикацией:** после разрешения команды проверить HTTPS, разрешение камеры, модель/WASM, SPA-маршруты, чистый профиль и мобильный браузер. | Демо проходит от вопроса до статуса COMPLETED без ручного исправления состояния; сборка и тесты зелёные; опубликованная ссылка проверена только после решения о деплое. |
| **Вся команда** | Уточнить у организаторов точный дедлайн, формат сдачи и доступ жюри к приватному репозиторию; распределить говорящих, подготовить короткое видео/скриншоты на случай отказа камеры. | Есть единый сценарий показа и список обязательных артефактов с ответственными. ## Рекомендуемый порядок до демо

1. **Стабилизировать реальную камеру.** A + B + C вместе проходят шесть жестов и записывают проблемы. Исправлять только воспроизводимые сбои, которые мешают основному пути.
2. **Пройти сквозной сценарий.** D проверяет вопрос медсестры → 👍/👎 → ответ в dashboard → WATER/TOILET с подтверждением → статус обратно пациенту → PAIN/HELP с отменой.
3. **Закрыть понятность интерфейса.** C исправляет текст или расположение элементов, которые мешали участнику пройти тест; A/B проверяют, что подсказки совпадают с фактическими позами.
4. **Собрать презентацию.** Показывать реальный путь, архитектуру и ограничение: MediaPipe даёт ориентиры, а классификация, удержание, подсказки и FSM написаны командой. Подготовить скриншоты ключевых шагов как запасной вариант.
5. **Публикация — отдельно.** После готовности и разрешения команды D проверяет финальную ссылку. До этого локальный сервер остаётся основным стендом.

## Как запустить и перепроверить

```bash
npm ci
npm run dev
npm test
npm run typecheck
npm run build
```

Открыть URL, который напечатает Vite. Для камеры нужен `localhost` или HTTPS и разрешение браузера. Для быстрого сценария без камеры открыть `/` с `?debug=1` **в dev-режиме**; этот режим не входит в production-сборку. Перед демо пройти тот же путь без mock. Видео обрабатывается локально; по transport передаются семантические события (вопросы, ответы, запросы, статусы), а не кадры камеры.

**Следующее обновление документа:** после реального прогона и подтверждения требований сдачи проставить фактические результаты, точный дедлайн и ответственных по именам. Не заменять результаты тестирования предположениями.
